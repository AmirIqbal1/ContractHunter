# Architecture

```text
apps/web          Next.js UI, API routes, scanning runner, verification planner/interpreter
packages/core     Domain models, Zod schemas, configuration, safety rules
packages/db       Drizzle schema and SQLite repository functions
packages/scanners Dependency/compiler managers, scanners, parsers, workspace builder, worker protocol
docker/verification-worker.ts  Networkless deterministic Forge and Echidna controller
contracthunter-data-init       One-shot, networkless tool-home directory initialization
data volume       SQLite, cloned repositories, trusted compiler cache
verification-workspaces volume  Generated harnesses only
verification-ipc volume         Group-restricted Unix socket only
```

The application is a TypeScript monorepo. SQLite/Drizzle stores scans, findings, investigations, AI records, hypotheses, and verification history. Cloned repositories live below `REPOSITORY_DIR`; persistent data is below `DATA_DIR`. Docker provides the production runtime and persistent data volume.

```text
UI/API → runner → repository preparation → compiler resolution
                 → Slither → Aderyn → correlation → completed static scan
                 → optional AI analysis → optional specialist review
                 → hypotheses → optional plan → explicit local verification
```

The scanning runner is intentionally small and single-instance; interrupted jobs are marked failed after restart. Static scanning is completed before optional AI stages. A one-shot, non-root data initializer ensures the trusted-cache directory is usable before the worker starts, including when Compose pre-creates an empty root-owned subpath during container creation. For verification, the web service validates persisted evidence, copies an allowlisted source closure, generates a deterministic Foundry harness/configuration, validates hashes, and sends bounded identifiers to the worker over a Unix-domain socket. The worker revalidates the workspace and trusted compiler, then executes fixed Forge arguments under `prlimit` without networking. It returns execution facts only. The web interpreter creates dynamic evidence and applies the hypothesis lifecycle rules. There is no Docker socket, dynamic container creation, or nested Bubblewrap execution.

## v0.2.0 Milestone 1: executable invariant foundations

`ExecutableInvariantPlan` is a separate strict core schema from the historical `VerificationHarnessPlan`. It carries trusted scan, hypothesis, commit, and compiler identity and has `fuzz-property` and `stateful-invariant` modes. The new internal generator validates referenced functions and getters against the primary Solidity contract through the shared conservative source-signature validator. The existing verification planner also uses that validator, preserving its historical parsing behavior. The invariant workspace builder reuses the existing bounded, allowlisted source closure and writes ContractHunter-owned Solidity, `foundry.toml`, source hashes, a canonical plan hash, and a strict invariant manifest. The historical verification builder and manifest format are unchanged.

A fuzz property has one generated `testFuzz_<name>` call with `uint256` and `bool` inputs. A stateful test deploys a handler with named actions; each action maps to one validated function on a named instance. A small ContractHunter-owned target registration helper provides `targetContract` and `targetContracts()` in the shape Foundry uses for invariant discovery. No forge-std download or repository-controlled helper import is needed.

## v0.2.0 Milestone 2: worker execution and evidence

`buildInvariant` now writes a version 2 invariant manifest containing the bounded canonical plan. The worker validates the manifest against its own plan, regenerates the harness and Foundry configuration from source, hashes every source, and refuses symlinks and unexpected files before execution. The historical version 1 verification manifest and worker path remain supported separately. The strict Unix-socket request has an explicit `execute-invariant` command with identities, mode, plan hash and fixed limits; it accepts no executable, arguments or environment.

The worker reuses the trusted compiler resolver and executes `/usr/local/bin/forge test --json` inside the workspace via `prlimit`, offline and without FFI. Forge 1.7.1 rejects combining `--json` and `--color never`; `NO_COLOR=1` remains set in the worker-owned environment. The bounded JSON parser requires the exact generated test names, assertion failure marker, counterexample shape and exit-code relationship. Web maps each result to `held-within-bounds` or `counterexample-found` property evidence. A separate `executable_invariant_runs` table records immutable runs without updating hypothesis status; Milestone 3 exposes the reviewed manual endpoint/UI workflow.

## v0.2.0 Milestone 3: reviewed proposals

The manual hypothesis flow now separates AI invariant proposal generation, server validation, and local execution. AI output uses a strict semantic proposal schema derived from the invariant plan's safe operation schemas. The canonical invariant capability profile supplies the prompt and bounded source context. The server selects relevant source from validated hypothesis/investigation/invariant evidence and import closure, requires one compatible trusted compiler, injects persisted identity, and runs the existing plan schema and Solidity signature validator before storing a canonical plan hash. Source hashes in proposal history bind later validation to the source the user reviewed.

`executable_invariant_proposals` stores each generation attempt with status, plan/hash when valid, provider/model/prompt, context statistics, usage, duration, and safe failure category. The hypothesis page shows the proposal and limits before enabling explicit validation; the run endpoint accepts only a persisted proposal ID and revalidates it before calling the Milestone 2 service. The existing structured verification path remains separate. No invariant evidence changes hypothesis status.

## v0.2.0 Milestone 4: deterministic replay and reviewed lifecycle

Invariant execution now records `propertyOutcome` separately from `hypothesisRelation`. A held property is neutral to the vulnerability hypothesis. A discovered violation is initially unreviewed. The only supported proposal relationship is `hypothesis-predicts-property-violation`: if the vulnerability hypothesis is true, the property is expected to be breakable. AI explains this relationship but cannot grant evidence authority.

Typed Forge 1.7.1 counterexamples use canonical serialization and SHA-256 identity. Fuzz values are named `uint256`/`bool` values. Stateful cases are ordered action IDs with typed parameter values; generation maps every action back to the original invariant plan. A replay artifact embeds authoritative scan, hypothesis, proposal, run, commit, compiler, invariant-plan, property, parser and counterexample identity. `InvariantReplayGenerator` creates one fixed `testReplay_*` test that passes only when the expected violation is observed. Replay has no fuzzing and accepts no browser-supplied values.

The existing worker protocol has a strict `execute-invariant-replay` branch. Each attempt gets a new replay-run ID and freshly generated workspace; web normalizes the workspace-specific fingerprint back to the immutable artifact ID and checks source, harness, config, replay-plan and counterexample identity before calling the worker. The worker independently regenerates and hashes the workspace, resolves the same trusted compiler, and runs fixed offline `forge test --json` under `prlimit`. Results are `reproduced`, `not-reproduced`, `failed`, or `refused`; a nonzero process exit by itself is never reproduction. Replay artifacts, runs, reviews, authoritative evidence, and lifecycle transitions are immutable linked records. Both historical structured verification and reviewed replay call the same centralized lifecycle authority.

## v0.2.1 Milestone 1: Echidna compatibility engine

Foundry remains the historical invariant engine. A separate `execute-echidna-invariant` worker operation accepts bounded identities and a canonical plan hash. Its version 3 manifest embeds the plan, source closure, deterministic harness/configuration hashes, seed, exact Echidna 2.3.3 compatibility build ID and binary hash, compiler identity, and fixed limits. The worker regenerates the harness and config, rejects extra files and symlinks, resolves the same cached trusted solc, then invokes `/opt/contracthunter/echidna/echidna` with a fixed argv under the existing `prlimit` and container isolation. The patched binary emits one strict JSON document with typed property names, terminal outcomes, stop reason, seed, and bounded transactions. The worker parser cross-checks property set, seed, version, outcome, and exit code.

The initial compatibility validator supports stateful plans with one no-argument deployment, generated uint256/bool actions, and current uint/balance equality assertions. It accepts multiple properties. It rejects actors, explicit callers, setup calls/funding, address assertions, caller/environment-sensitive source, and fuzz-property mode with explicit reasons. No plan supplied Solidity or Echidna config is used. The deterministic seed is the first 48 bits of the canonical SHA-256 plan hash. Exact zero-value, zero-delay Echidna action sequences map to the existing canonical counterexample type and Foundry replay generator; otherwise replay availability is false while the property failure remains recorded. A bounded held result is neutral to the hypothesis, and all existing relevance and lifecycle rules remain unchanged.

The compatible binary is built from the included upstream v2.3.3 archive and a four-file output patch using upstream's locked Nix flake. A serial build yielded byte-identical static ELF hashes in two clean containers. The worker image also carries a hash-locked Python `crytic-compile` runtime to invoke the exact trusted solc path. See `third_party/echidna/README.md` for source, build, hash, and license details. This milestone exposes an internal builder/client path only; AI and UI do not choose the engine.

Foundry runs store parser/tool/config identity; Echidna runs store bounded build/config/harness/seed audit metadata.

Both engines expose the same property outcomes and separate hypothesis relations. An exact Echidna sequence enters the existing deterministic Foundry replay service. Replay artifacts bind source engine, invariant run ID, and counterexample hash; historical Foundry plans retain their original hashes. Reproduction plus explicit relevance review still enters the single centralized lifecycle authority. A non-mappable Echidna sequence remains a `counterexample-found` observation with replay unavailable.

## v0.2.2 Milestone 1 Part 1: verification strategy assessment

`packages/core/src/verification-strategy-assessment.ts` defines four strategy profiles separately from engine, invariant plan mode, and property outcome. Their supported requirements follow the current structured and invariant plan schemas and the narrow Echidna compatibility validator. A small exact `(scanner source, detector ID)` registry maps confirmed rule families to bounded necessary requirements. The read-only database adapter follows a hypothesis's persisted investigation IDs, checks scan and primary-contract identity, and passes only normalized finding metadata to the pure assessor. It does not parse hypothesis prose, scanner descriptions, repository source or comments.

Each strategy receives `compatible`, `incompatible`, or `unknown` with stable reason codes. Compatibility means only that the known requirements fit the abstract plan capability profile; source signatures, compiler availability, concrete plan validation, and worker execution remain separate checks. Unknown links, contract identity, and unmapped rules fail to `unknown`; a known unsupported requirement may still establish `incompatible`. This assessment is internal and advisory. Existing AI prompts, proposal generation, routes, UI, replay, evidence and lifecycle paths are unchanged.

## v0.2.2 Milestone 2 Part 1: computed verification targets

`buildVerificationTargetGroups` is a pure, deterministic advisory calculation. An exact registry maps only source/detector pairs already admitted by strategy assessment to normalized root-cause families: access control, reentrancy, tx.origin authorization, unchecked low-level call, timestamp dependence, and arithmetic order. A candidate must have valid same-scan investigation links, resolved primary contract/path, mapped findings that match that primary identity, and a function or source region. Findings on the same normalized family/contract/path/function group only when their source intervals overlap. Without intervals, grouping requires the same investigation and function. Multiple incompatible target claims or missing structured identity isolate the hypothesis. Existing AI hypothesis groups use different signals and are not reused as authoritative verification targets.

A target ID is a stable hash of structured identity. Every retained hypothesis appears once; ambiguous or unmapped hypotheses receive independent `unknown-family` targets. Members and groups are sorted deterministically. The planning representative is selected by validated source linkage, distinct scanner linkage, linked investigation count, mapped requirements, then compatible strategy count; the hypothesis ID is the final tie-break. Strategy counts describe planning capability, not vulnerability evidence. A bounded public mapper emits closed family/reason codes, a safe contract identifier, representative ID, and related count, without source paths or scanner prose. `listPersistedVerificationTargetGroups` reads existing hypothesis, investigation, and finding rows and writes nothing.

`buildInvariantPropertyTargets` separately hashes exact canonical generated property semantics, including scan/commit/compiler/source closure, setup, action, observations, and assertions. It excludes cosmetic property and assertion labels and hypothesis identity. This supports conservative property reuse analysis across generated proposals; it does not infer semantic equivalence when actions or observations differ. `listPersistedInvariantPropertyTargets` is read-only. There is no migration, public target UI, planning redirect, provider call, verification run, evidence creation, or lifecycle transition in Part 1.

## v0.2.2 Milestone 2 Part 2A: advisory target and planning history

`GET /api/hypotheses/:id/verification-target` and the hypothesis page use the same read-only discovery service. On every request it reloads the hypothesis and current scan, recomputes Part 1 target groups, and finds the requested member. The public result contains only the opaque target ID, closed family/confidence/reason, representative and related hypothesis IDs, strategy readiness lists, and bounded planning candidates. It does not expose scanner prose, repository source or source paths. A nonrepresentative may navigate to the representative; direct planning stays available.

Candidate discovery reads immutable structured planning attempts and invariant proposals of current group members. It requires a currently compatible exact selected strategy, matching plan mode, scan, commit, trusted compiler list, primary contract/path and target function. Invariant proposals additionally require every exact property-target ID to be present for the requested hypothesis; legacy proposals without selected strategy are never eligible. A plan is labeled `validated-at-execution` only when matching persisted run history exists, because standalone validation responses are not stored. Generated-only history remains ineligible. `eligible` is an advisory candidate label, not a claim of current executable validity or vulnerability validity. `stale` and `incompatible` expose bounded reason codes. Ordering is eligible first, then validated history, newest creation time, and stable artifact ID. No rows are written; no AI, worker, plan binding, execution, replay, evidence or lifecycle action occurs. Part 2B must perform fresh source-byte validation and explicit rebinding before reuse; Part 2A does not compare live source bytes to historical context hashes.

## v0.2.2 Milestone 2 Part 2B-00A: scan source snapshots

After the repository commit is resolved and permitted dependency preparation completes, the scan runner captures raw `.sol` bytes before compiler preparation and asynchronous planning. It seeds the allowed source universe from `src`, `contracts`, and `lib`, traverses only safe in-repository directories, and follows the verification workspace builder's import parser/resolver to add required `node_modules` Solidity files. Unrelated package files, build outputs, hidden secrets, and repository metadata are excluded. Source keys are normalized repository-relative Solidity paths; host checkout paths are never stored as identity. Internal directory symlinks are permitted only when their resolved targets remain inside the prepared repository's allowed source roots and have no loop or duplicate physical source alias. Solidity file symlinks and escapes fail closed.

Migration `0005_v0_2_2_scan_source_snapshots` adds a scan-owned manifest and raw-byte BLOB rows. Its schema is `contracthunter-scan-source-snapshot-v1`; every file records its canonical key, exact byte length, and SHA-256 over raw bytes. The manifest stores the resolved commit, file count, total bytes, and finalization time. Limits are 100 files, 2 MiB per file, 5 MiB total, 500 characters per key, and 20,000 traversed entries. Capture failure leaves no finalized snapshot; insertion and finalization share one SQLite transaction. Database triggers prevent updates or membership changes after finalization. A scan deletion cascades to its snapshot; the separate verification-workspace retention command does not manage scan records.

`getScanSourceSnapshot`, `listScanSources`, and `getScanSource` read the database only, check scan/commit binding and stored byte hashes, and report legacy/unavailable scans explicitly. No historical scan is backfilled from a checkout. This identity is scan-time source provenance, distinct from later execution-workspace hashes and the future generation-time source-closure fingerprint. Existing scanners still use their prepared checkout, and planning/import/execution consumers are not switched here. Part 2B-00B will unify their closure resolution against the snapshot before fingerprinting or plan reuse can be admitted.

## v0.2.2 Milestone 2 Part 2B-00A4: authoritative compilation provenance

Scanner analysis and ContractHunter authoritative compilation are separate trust domains. Slither and Aderyn retain native project detection and may analyze more projects than the authoritative verification path. ContractHunter currently supports only `plain-solidity-exact-pragma-v1`: snapshot Solidity under `src` or `contracts`, one identical exact Solidity pragma per file, no root Foundry/Hardhat/remappings configuration, and an already cached trusted compiler. Explicit Foundry configurations remain authoritative-unsupported until their remappings and environment-sensitive behavior can be represented without inference; executable Hardhat configuration is `dynamic_build_configuration`. Static findings remain available when authority is unsupported.

After scanner execution, the scan runner independently derives a version from the immutable snapshot, resolves the exact cached solc-select artifact, hashes that artifact, and sends fixed `--standard-json` input containing only snapshot bytes. Empty remappings, disabled optimizer, fixed output selection, a bounded process timeout/output, and no file callback make the probe independent of repository scripts, scanner build detection, RPC, wallets, and AI. Compiler output must contain exactly the submitted source-unit names and no errors. The finalized `contracthunter-compilation-manifest-v1` binds scan and resolved commit to compiler version/artifact SHA-256, profile, source/library roots, remappings, and every source-unit name, snapshot key, raw hash, byte length, and compiler-reported contract names. One source unit maps to one snapshot key; duplicate/ambiguous identities and absent snapshot files are rejected. The source snapshot remains the authority for bytes after checkout deletion.

Migration `0006_v0_2_2_compilation_provenance` adds an immutable scan status, source-unit rows, and per-finding scanner alignment rows, all scan-owned with cascade deletion. Status is `supported` or `unsupported` with a closed reason. Historical scans have no row and read as `legacy_or_unavailable`; no checkout backfill occurs. Supported status and source units commit together only after a successful probe. Scanner version, detector ID, bounded reported source identity, canonical source key, and contract resolution are recorded independently for each finding. Exact source-unit or repository-relative identity, including an absolute path proven below the known checkout root, may align; a basename, missing source, or path outside the checkout does not. Alignment means the finding references a source in ContractHunter's compiled universe, not that the scanner used identical compiler machinery. Future authoritative verification needs supported provenance, aligned source, and unambiguous contract identity. Existing planning and execution paths are unchanged in this part; Part 2B-00B must consume snapshot-backed closures and apply the new eligibility gate before reuse.

## v0.2.2 Milestone 2 Part 2B-00B-1: authoritative source consumption

`contracthunter-authoritative-source-closure-v1` is resolved from the finalized compilation manifest, scanner alignment, and immutable scan snapshot rows. It contains scan/commit/compiler identity, one exact target source unit, and each transitive import's canonical source-unit name, snapshot key, raw bytes, SHA-256, and byte length. The resolver supports only `plain-solidity-exact-pragma-v1` imports that resolve exactly to manifest units under `src` or `contracts`. It rejects missing or altered bytes, unsupported imports, ambiguous or unaligned targets, invalid UTF-8 for planning, and bound overruns. Cycles use a visited set and output has canonical source-unit order. There is no aggregate fingerprint or new database table in this part.

Structured and invariant proposal services use this same resolver for supported scans, including manual generation routes. Supported workspace builders write exact BLOB bytes at source-unit paths and use ContractHunter-owned configuration with `src = "."` and automatic remapping discovery disabled. Structured verification, Foundry and Echidna invariant execution, and replay receive the same closure through their services; worker isolation and historical artifacts are unchanged. Legacy and unsupported scans use explicitly marked legacy checkout paths for compatibility. The authoritative branch has no checkout fallback. Fingerprint persistence is the next gate before plan reuse.

## v0.2.2 Milestone 2 Part 2B-00B-2: generation-time closure fingerprint

The pure core helper `fingerprintAuthoritativeSourceClosure` computes `contracthunter-source-closure-fingerprint-v1` after snapshot/manifest byte and length verification and before a planning provider request. It independently rehashes each raw Buffer and rejects malformed hashes, duplicate source-unit names or snapshot keys, missing targets, and bound overruns. Its SHA-256 stream uses UTF-8 strings prefixed by unsigned 64-bit big-endian byte lengths: fingerprint schema, authoritative closure schema, compilation profile, target source unit, then unsigned 64-bit file count. Canonically source-unit-sorted files each contribute framed source-unit name, framed snapshot key, unsigned 64-bit raw byte length, and the 32 raw SHA-256 bytes. No decoded text or checkout path enters the aggregate.

Both planning services call this one helper. New structured planning attempts, including manual requests and selected-strategy requests, and new Foundry/Echidna invariant proposals persist the same schema, full digest, file count, and total bytes on their own append-only history rows. Provider failure rows retain the already computed fingerprint. Migration `0007_v0_2_2_source_closure_fingerprints` adds nullable columns and insert/update guards; prior rows remain null and readable. The invariant proposal context's older source-hash map keeps its existing context-validation semantics and is separate from this aggregate. Scan ID, resolved commit, compiler artifact identity, and selected strategy are independently persisted or checked, never mixed into the closure fingerprint. Candidate discovery treats null fingerprint as unavailable. It does not admit reuse; a future explicit backend must still compare all identities, validate current bytes, and safely bind the selected artifact.

## Planned v0.3: Fork & Impact Engine / Impact Lab

Impact Lab is a downstream reproduction and measurement system, not a replacement for static scanning, Foundry/Echidna verification, counterexample replay, relevance review, or lifecycle authority. A researcher explicitly links a candidate finding or hypothesis to a deployed contract, network and exact fork block. A separate bounded engine runs a reviewed PoC against a ContractHunter-managed local Anvil fork, then records selected before/after state, call traces, transactions and asset flows. Existing verification workers stay networkless; the future fork runtime has a separate, tightly scoped upstream read channel and a local execution channel. The GUI cannot become the source of truth for experiment semantics.

The future domain model will bind finding, chain ID/network, fork block and block hash, targets, disposable attacker identity, scenario and privilege assumptions, transactions, outcomes, trace/state-diff/asset-flow observations, impact estimates, timestamps and reproducibility metadata. Define schemas and engine behavior first, then a CLI/service, API, and finally the existing web application's Impact Lab GUI. Fork outcome, impact estimate and vulnerability lifecycle remain independent until explicit evidence integration is reviewed. See [Impact Lab](impact-lab.md) for the milestone and export design.
## v0.2.2 Milestone 2 Part 2B-1A: explicit planning reuse admission

The two bodyless POST routes select a persisted structured planning attempt or invariant proposal by ID. `PlanningReuseService` performs admission inside a SQLite transaction. It reloads the requested and source hypotheses, scan, compilation provenance, scanner alignment, investigation links, target groups, and strategy assessment. It resolves the current authoritative closure from immutable scan snapshot bytes and recomputes `contracthunter-source-closure-fingerprint-v1`. The original artifact must have a generation-time fingerprint with identical schema, digest, file count, and total bytes. Scan and resolved commit must match exactly; trusted Solidity version and compilation artifact remain independent compiler provenance. Exact current target membership and strategy compatibility are required, including for a nonrepresentative hypothesis. Invariant proposals also require matching canonical mode and exact property target; Echidna compatibility is checked again against current source.

Admission reads persisted canonical plan JSON, never provider prose. Structured plans receive a new hypothesis ID and pass the current static source and harness validator. Invariant plans receive a new hypothesis ID and pass the current generator and property checks. Existing execution history supplies a validation witness for the source artifact, but no validation or execution state is copied. Each new row stores its own current fingerprint and co-located immutable reuse provenance (`reuse_source_artifact_type`, `reuse_source_artifact_id`, `reuse_target_id`, `reuse_compiler_artifact_sha256`, `reuse_created_at`). One insert inside the admission transaction makes artifact and provenance atomic. Reused rows have no provider identity or token usage. Historical rows retain null reuse fields. Ordinary generation and execution APIs remain separate. The UI does not yet expose a Reuse action.
