# Protocol Intelligence / ProtocolGraph

## Security View projections (Phase 7A)

`contracthunter-security-view-v1` derives seven read-only projections from the validated static graph artifact: Money Flow, Permissions, Oracle Flow, External Calls, Upgradeability, Attack Surface and Findings. Each result carries the scan and graph IDs, canonical node/edge references, bounded static annotations, inclusion reason IDs with source/evidence, factual counts, warnings, a derivation version and a canonical content hash. The results are computed on read; no graph identity changes and no migration is needed. `GET /api/scans/:id/protocol-graph/security-views/:view` accepts only the seven closed view names. Phase 7B will render them; the Protocol Map has no new Security View UI in Phase 7A.

Money Flow includes compiler-backed `token-transfer` and `native-transfer` characteristics, exact matching call sites and any explicit static `transfers` edges, preserving each underlying edge kind. Current transfer-like characteristics cannot prove deployed token identity, asset direction, amount, mint/burn meaning or profit/loss; only a future explicit transfer edge could support directional presentation. Permissions includes proven role-to-function `controls` edges; current production extraction proves only the exact `_owner`/`msg.sender` modifier guard, not AccessControl, pause or governance semantics. Oracle Flow requires an explicit `oracle-like` trait or known oracle node with evidence. Today's static extractor does not create those traits, so a name such as `OracleThing` yields no oracle projection. The model can project them when a future trusted extractor supplies them. External Calls distinguishes high-level, CALL, STATICCALL and DELEGATECALL call sites, target context and unresolved targets. Upgradeability requires a proven proxy/upgrade relationship; a standalone delegatecall stays out. Attack Surface includes actual entry points, payable and proven state-writing entry points, static external calls, assembly/callback traits when present, transfer traits and exact findings. Findings includes only exact graph finding links and bounded same-scan metadata. An unmapped-finding count is unavailable from the static artifact and is not fabricated.

Reasons are stable explanation keys for later educational copy; they are not vulnerability conclusions. Counts describe static facts, not risk scores. The deriver follows direct graph edges only, terminates on cycles, caps each view at 5,000 nodes, 20,000 edges, 20,000 annotations, eight reasons per item and 32 warning kinds, and reports clipping or partial analysis. Same graph artifact, view type, derivation version and optional finding metadata yield the same content hash; the view ID binds the immutable graph artifact and derivation version. Current finding status metadata may change independently of static graph truth. Static Money Flow, calls and writes remain separate from future observed Impact Lab asset flow, D1 traces and C1 state diffs. No AI, ranking, exploitability inference or lifecycle mutation is involved.

## Visual Function Explorer (Phase 6B)

From a completed hunt, open Protocol Map, select a contract, open Contract Explorer, then select an exact function signature. `/hunts/:scanId/contracts/:contractId/functions/:functionId` validates the scan, contract and canonical function IDs. The page renders the Phase 6A model as a vertical **SOURCE-ORDER VIEW** with operation cards, exact snapshot-source links, a synchronized selected-operation detail/source panel, callers/callees and exact function findings. It uses a structured React timeline rather than the Protocol Map graph renderer. Beginner and Researcher display densities share one model; fixed product copy explains operation kinds and review cues. Search, category filters and a bounded large-function mode change presentation only.

Source order is not runtime control flow. Branch, loop and try/catch markers do not prove a path, and a write-after-call cue is a source-position fact rather than a reentrancy verdict. Unresolved targets remain unresolved; token-transfer-like facts do not establish an asset, and delegatecall alone does not establish a proxy. Function-level findings receive no guessed operation badge. Older or incomplete graph artifacts show partial-analysis warnings while retaining known facts. The optional preview uses at most 4 KiB of strict UTF-8 from the checksum-matched immutable scan snapshot; otherwise exact source links remain. C1 state changes and D1 execution traces remain separate future overlays. There is no arbitrary function-to-Impact-Lab execution action.

## Function Explorer backend (Phase 6A)

`contracthunter-function-explorer-v1` is a frontend-independent, bounded one-function read model derived from the validated static ProtocolGraph artifact. Exact scan, contract and function IDs determine ownership; overloaded signatures stay distinct. New graph generations retain at most 256 compiler-AST syntax facts per function (conditions, reverts, branches, loops, try/catch, event emissions, returns and assembly), each with canonical source range and a SHA-256 identity for its source bytes. Existing graph edges and function facts supply internal/external calls, low-level/delegate calls, modifier invocations, state-variable references and token/native-transfer-like characteristics. Calls with unresolved targets remain explicitly unresolved. The model caps operations at 512, relationships at 512 per direction, state refs at 256 per mode, findings at 128 and modifiers at 32; overflow and legacy missing syntax facts produce partial-analysis warnings.

Operations are sorted by **source location**. This is a source-order view, **not** a control-flow graph or guaranteed runtime sequence. The current persisted Slither detector JSON does not provide reliable machine-readable CFG/basic blocks. Branches and loops are markers, not executed paths. Write-before/after-call review cues compare source positions only and do not diagnose reentrancy. Modifier names alone do not prove authorization; callback/override relationships are deferred until exact structural evidence exists. State refs inherited from Phase 3 may be collapsed by variable, so the model marks their call-site analysis partial. There is no risk score or vulnerability authority.

`GET /api/scans/:id/protocol-graph/contracts/:contractId/functions/:functionId` returns the bounded model and, when available, at most 4 KiB of strict UTF-8 function source from the checksum-matched immutable scan snapshot. Historical graphs stay readable with partial analysis; no backfill or migration is needed. Function flow is derived on read, so new extraction rules produce new immutable graph generations. Future D1 trace and C1 state overlays can reference exact function/operation IDs without changing static facts. The Phase 6B page renders this model as a bounded visual source-order timeline.

## Status and purpose

**Phases 1–6 and 7A implemented:** the frontend-independent ProtocolGraph, deterministic Repository Mapper, immutable static graph, Protocol Map UI, Contract Explorer, Function Explorer model/API/UI and Security View derivation/API. Phase 3 uses finalized Repository Maps and, only for the existing supported exact-pragma compilation profile, a checksum-verified trusted `solc --standard-json` AST query over immutable source snapshots. Unsupported profiles receive map-backed contract nodes and explicit warnings rather than guessed calls. Interactive Security Views (Phase 7B) and dynamic overlays (Phase 10) remain planned. No AI call or vulnerability authority was added.

## Contract Explorer UI (Phase 5)

Select a contract, interface or library on `/hunts/<scan-id>/protocol-map`, then choose **Open Contract Explorer**. The dedicated `/hunts/<scan-id>/contracts/<canonical-graph-node-id>` page uses the validated artifact from that scan and exact graph IDs; a wrong ID or another scan's ID returns 404. **Back to Protocol Map** and **Show in Protocol Map** preserve the scan and selected graph node. The browser receives a bounded one-contract view, not the whole graph.

The header shows declaration/classification, canonical source, proven proxy traits and exact finding count. A factual overview reports entry points, callers/callees and extracted relationships. **Review cues** expose structural security interest without a risk score or vulnerability conclusion. Functions are searchable and filterable by signature, entry point, finding, external call, known state write and payable status; the list initially renders 60 and reveals 60 more on request. Entry points mean functions proven public/external, including receive/fallback when represented. Function rows retain modifiers, state access/transfer/low-level facts, exact finding badges and source links. Relationship sections distinguish incoming/outgoing/internal calls, inheritance, interfaces, library use, proven proxy/upgrade and control facts, with bounded source/provenance detail. Unresolved targets remain explicitly unresolved. State variable read/write facts are shown where available; storage slots and event emissions are not inferred.

The page uses only exact finding links to existing finding detail routes and the Phase 4 immutable source excerpt route. When snapshot bytes are available it also shows a bounded 12-line declaration preview. The read model caps functions at 2,000, each relationship category at 1,000 and state/finding details at 500; full graph counts remain visible with a limit notice. A token-transfer-like operation does not establish an asset identity; a delegatecall does not prove proxy status; a modifier name does not prove authorization. Semantic purpose remains unclassified unless deterministic classification exists. An Impact Lab launch action is unavailable because this page has no safe contract-to-reviewed-session authority; existing finding/hypothesis/session rules remain intact. C1/D1 runtime overlays belong to Phase 10. Function rows link to the Phase 6 Function Explorer for deeper static source-order detail.


## Protocol Map UI (Phase 4)

Open a completed hunt and choose **Open Protocol Map**, or visit `/hunts/<scan-id>/protocol-map`. The server loads the immutable validated graph artifact; the client adapter maps its existing static nodes/edges to React Flow without changing core graph types. Dagre provides a deterministic left-to-right layout. The canvas starts at contract/concept level; functions remain in the selected contract preview. React Flow provides zoom/pan, fit, keyboard-selectable graph elements and a minimap. A textual relationship list and detail panel provide non-canvas access.

The toolbar searches contract names, function signatures and canonical source units. Presets are All, Core protocol, External calls, Upgradeability and Findings. Controls can hide interfaces, libraries and dependencies, select findings-only, and toggle relationship kinds. Counts report visible versus total non-function nodes and cross-node edges. At more than 90 nodes, interfaces and libraries start hidden; above 240 nodes, core/periphery and direct dependencies become the default. Rendering is capped at 600 nodes and 1,600 edges with a visible clipping notice; filtering can narrow the view. Compound grouping is deferred; classification/source-root information stays available in labels and details.

Node styles distinguish core, periphery, interface, library, role, proxy traits and unresolved external actors by border, shape/text and badges rather than color alone. Edge labels and detail panels show kind, caller/callee signatures, exact canonical source location, reason and extractor evidence. A proxy badge appears only on a graph node carrying the proven proxy characteristic; delegatecall alone does not add it. Search can reveal a hidden contract. Selection highlights direct topology, with callers/callees controls; it does not infer attack paths. Findings badges use exact graph references and link to existing finding detail pages. Unresolved calls and extraction warnings are presented explicitly.

Source actions open `/hunts/<scan-id>/source?unit=<canonical-unit>&line=<line>`. The server admits only source units already in the validated graph and displays a bounded excerpt from the immutable scan snapshot. If no snapshot is available, it reports that limitation and does not read a mutable checkout. Graph-derived text is rendered through ordinary escaped React text, never raw HTML. The UI is navigation data only: no finding verification, evidence, severity, confidence or lifecycle updates.

The Map remains the overview and the Explorer is its contract drill-down. Full Beginner Mode, final Security Views, asset-flow inference, Impact Lab runtime overlays and AI explanations remain future work.

## Repository Mapper v1

`contracthunter-repository-map-v1` uses `contracthunter-repository-mapper-v1` rules. A map binds its deterministic ID to scan ID, resolved commit, ruleset and a SHA-256 source-universe digest. The digest includes sorted mapped paths and Solidity byte hashes/authority. Files have stable scan/path IDs, source-root membership, `snapshot`/`reported`/`path-only` provenance, parse status, zero or more source-linked declarations, bounded imports, classification with machine-readable reasons, and exact aligned finding references where available. The map includes a class-count and directory-count overview, roots with provenance, and bounded warnings. Phase 3 consumes this finalized map through the `RepositoryMapToProtocolGraph` handoff and should not rediscover classifications.

The mapper traverses at most 20,000 entries and maps at most 10,000 files, 5,000 Solidity files and 128 roots. It reads at most 2 MiB per Solidity file and serializes at most 8 MiB of metadata. A file has at most 128 declarations and 256 imports; a map retains at most 256 warnings. No source body is copied into the map. Symlinks are skipped, including cycles and escapes; unsafe names are skipped with a warning. Non-Solidity files are classified from path metadata only. Snapshot-backed Solidity uses the immutable persisted bytes even if the checkout differs. Where no snapshot exists, bounded regular checkout files are read and explicitly marked `reported`; no authoritative source identity is invented for historical scans.

Source roots are discovered from actual Solidity paths, including conventional `src`, `contracts`, `protocol`, test/script roots, package-level `packages/<name>/src|contracts|protocol`, and vendored `lib/<name>/src`. Vendored `lib/<name>/src`, `node_modules` and `vendor` are dependency roots; a project-owned `lib/` remains a project root. The mapper does not recursively inventory checkout `node_modules`; only dependency Solidity reached by the existing immutable snapshot can appear from that tree. Multiple roots remain distinct. Import resolution accepts only exact repository-relative source paths or safe direct source-unit paths already in the map. Remapping aliases, dynamic Hardhat behavior and absent sources remain unresolved or unsupported, never guessed. Cyclic imports are data, not traversal recursion.

The closed Phase 1 classification vocabulary is reused: `core`, `interface`, `library`, `mock`, `test`, `deployment`, `periphery`, `dependency`, `frontend`, `supporting`, `unknown`. Dependency, test, mock and deployment paths take precedence over declarations; an all-interface or all-library Solidity file receives its declaration class. An explicit `core` directory plus a lexically observed external/public entry point is required for the initial conservative `core` rule. An explicit `periphery` directory supports periphery; ordinary ambiguous production contracts remain `unknown`. Rules use exact path segments or `.t.sol`/`.s.sol`, not `Test`/`Mock` substrings. These are navigation facts, not a risk score or vulnerability probability.

The lexical pass masks Solidity comments and strings, checks balanced braces, and extracts top-level contract/interface/library declaration candidates, source line/column, simple inheritance names, public/external entry-point presence and import literals. It does not compile Solidity or validate its grammar. Detected unbalanced/unreadable input is `incomplete` with no declarations; balanced but compiler-invalid syntax may still yield candidates. Recognized declarations remain `solidity-lexical` evidence rather than compiler facts. Files may contain multiple declarations of different kinds. The existing compiler manifest supplies the authoritative contract-name check for its narrow supported profile; Phase 3 reconciles those lexical candidates with a trusted compiler AST only for the supported snapshot profile; other candidates stay explicitly unverified.

Phase 1's classification shape retains `automatic`, `automaticOrigin`, reasons, optional `override` and `effective`. `withRepositoryClassificationOverride` models a future researcher correction while preserving the automatic classification. The persisted automatic map has no override UI or mutation route in Phase 2. Override data must eventually be stored separately from immutable map generations; it must never modify scanner findings or source provenance.

After scanner alignment, the scan runner attempts to finalize the map. Additive migration `0014_protocol_repository_maps` stores bounded immutable JSON with a separate SHA-256 content hash and scan/commit/ruleset/source-universe columns. Reads validate the content hash, schema and binding. A failed or unsupported mapping attempt does not fail the established scanner result, and no map is fabricated for historical scans. `GET /api/scans/:id/repository-map` returns a finalized map or 404. Deleting a scan follows its foreign-key cascade; maps cannot otherwise be updated/deleted. No Impact Lab source/deployment link is invented: deployed bytecode hashes alone cannot establish a source-file match. Phase 3 can add only exact supported links.

Protocol Map and Contract Explorer are core research capabilities. The design principle is to make Web3 security complexity understandable visually while retaining the real Solidity and security terminology. A characteristic means **security interest / audit priority**, never vulnerability probability, severity or a confirmed bug.

## Versioned model and identities

`contracthunter-protocol-graph-v1` contains graph/scan ID, resolved commit, extractor version and producer versions, source-unit provenance, nodes, edges, file classifications and bounded warning codes. Graph/cache identity is a canonical SHA-256 frame over scan ID, resolved commit, schema and sorted producer versions. It never uses working-tree timestamps. The immutable static graph artifact is now stored by migration `0015_protocol_static_graphs` with a map-bound extractor version and canonical content hash. No mutable graph cache exists.

Node IDs hash scan ID + closed node kind + canonical semantic key. Repository contract keys include **full source-unit name and contract name**; function keys include the owning contract key and full signature. Edge IDs hash scan ID + closed relationship kind + endpoints + a relationship key such as source callsite identity. Two calls between the same contracts can remain distinct. Cycles are valid. Identity does not depend on layout or insertion order.

The closed node kinds are `contract`, `function`, `role`, `token`, `external-protocol`, `oracle`, `proxy`, `library`, `interface` and `external-actor`. Contract nodes carry qualified name, kind and classification; function nodes carry owner, signature, visibility, mutability, modifiers and entry-point state. Concept nodes have `known` / `likely` / `unknown` / `unclassified` identity and may explicitly reference a known repository contract. A token-like interface or variable name does not prove a deployed protocol or real-world role.

The closed edge kinds cover `calls`, `inherits`, `implements`, `uses-library`, `reads`, `writes`, `transfers`, `controls`, `upgrades`, `delegates`, `prices`, `external-call` and `finding-related`, plus future `executed-call`, `observed-transfer` and `state-changed`. The **base graph admits only static edges**; finding and runtime kinds are reserved for overlays. Every base edge needs bounded reason codes and evidence; call edges may identify exact caller/callee functions and source callsite. This supports a later “why are these connected?” explanation without embedding large hostile source text.

Source locations use the existing safe repository Solidity path vocabulary, exact line/column and optional byte range. Every referenced source unit must be declared in the graph. Its identity is either `authoritative` (snapshot key, raw SHA-256 and byte length present) or `reported` (no claim of authoritative binding). Evidence records producer origin/version, optional source range and bounded reference ID. Origins include ContractHunter parsing, Slither, Aderyn, compiler, Repository Mapper, findings, Impact state/trace and explicit manual override; finding and runtime origins are reserved for overlays and rejected from the static base. Traits such as `handles-assets`, `privileged-operation`, `oracle-dependent`, `delegatecall` and `token-transfer` require their own static evidence. `finding-present` is reserved for the later finding overlay. These are identifiers for explanation and transparent audit-interest factors, not scores.

Repository classification vocabulary is `core`, `interface`, `library`, `mock`, `test`, `deployment`, `periphery`, `dependency`, `frontend`, `supporting`, `unknown`. Classification retains its automatic value, origin and reason codes beside an optional manual override and effective value. Phase 2 implements deterministic discovery/classification and an override model; storage and UI for researcher overrides remain planned.

## Validation and overlays

Validation rejects duplicate or noncanonical IDs, dangling edges, invalid/missing source units, impossible function ownership, duplicate canonical function identity, unsupported node/edge kinds, unsupported graph extension fields and exceeded bounds. Limits are 5,000 source units, 20,000 nodes, 100,000 edges, eight evidence records and eight reasons per fact, 16 characteristics per node, 256 warnings and 10,000 entries per overlay. Validation indexes nodes/sources/edges once and accepts cyclic graphs. The graph model can represent a larger future source universe than today's 100-file snapshot; that does not make the current scan pipeline support it.

Overlays are separately versioned and graph-ID-bound. Finding entries refer to existing node/edge IDs. State entries refer to existing nodes plus a C1 diff/change ID. Trace entries refer to existing nodes plus D1 trace ID, transaction hash and call ordinal. Overlay validation rejects missing targets, duplicate entries, wrong graph identity and attempts to include extra graph fields. These are **interfaces**, not complete C1/D1 address-to-source adapters: address resolution, deployment matching and ambiguous/unmapped runtime calls still need explicit future policies. A runtime call cannot silently create a static contract node; an overlay never overwrites the base graph.

## Static graph extraction v1

`packages/scanners/src/static-protocol-graph.ts` composes finalized Repository Map declarations, supported trusted compiler AST facts, and exact aligned finding references. The extraction is server-side and uses no repository scripts, dynamic Hardhat configuration, terminal diagrams or DOT parsing. Existing Slither/Aderyn JSON remains finding data; the current scanner adapter does not expose structural call data, so Phase 3 does not claim Slither structural provenance. A trusted AST query checks snapshot membership, raw byte hashes and the cached compiler artifact hash, then asks only for AST machine output. Compiler failure leaves a map-only graph with unverified lexical-contract warnings; it does not invent structural relationships or change scan results.

The versioned `contracthunter-static-protocol-graph-v1` artifact wraps the Phase 1 base graph. Contract/interface/library nodes retain canonical source-unit and Repository Map classification; abstract status is explicit. Compiler-backed function nodes distinguish signatures, overloads, constructors, receive/fallback, visibility, mutability, modifiers and entry points. Compiler declaration references support exact internal/external calls, multiple call sites, inheritance/interface implementation and `using` or direct library use. Dynamic member calls and low-level call/staticcall/delegatecall targets remain unknown external actors plus bounded unresolved records. Function facts retain exact observed state-variable references, writes, low-level calls and conservative token/native-transfer syntax. They do not infer storage slots or asset flow.

Proxy classification requires both the exact EIP-1967 implementation-slot literal and delegatecall in the same contract. It records that structural evidence and an unknown implementation target; no deployed implementation address is inferred. Owner control is limited to an explicit `require(msg.sender == _owner)` modifier pattern with an address state variable and a referenced modifier invocation. Other AccessControl/role semantics are deferred. Import records stay in the Repository Map and are never recast as call edges. Exact aligned findings may attach by canonical unit and contract, with function attachment only for a unique line match; findings do not alter graph structure.

Identical static facts merge by deterministic semantic edge ID while retaining bounded multiple evidence records. Distinct call sites have distinct IDs. Nodes, edges, evidence and unresolved records are canonically ordered; `contentSha256` hashes the versioned artifact using recursive key sorting. Summary counts are facts: contracts, interfaces, libraries, functions, edges, external calls, entry points, proxies, delegatecalls, finding-linked nodes and unresolved relationships. Validation rejects broken bindings, unsupported types, duplicate IDs, missing nodes and exceeded Phase 1 bounds. Static source relationships never consume C1 state or D1 traces; their overlays remain separate.

Additive migration `0015_protocol_static_graphs` stores one immutable graph generation per scan/map/extractor identity with a separate stored-byte hash. `GET /api/scans/:id/protocol-graph` returns only a validated finalized artifact or 404. Historical scans have no fabricated graph. A scan with an unsupported structural profile still has its Repository Map and a bounded map-only graph. A changed extractor version or Repository Map identity must produce a new graph generation. The graph is research/navigation data, not hypothesis verification, severity, evidence or lifecycle authority.

## Extraction and UI path

Phase 2 discovers Solidity roots and classifies core/periphery/dependency/test files with reviewable reasons. Phase 3 now composes the finalized map, supported trusted compiler AST and aligned finding references. Slither's [Python API](https://github.com/crytic/slither/blob/master/docs/src/api/api.md) is a promising structured provider; its [printer list](https://github.com/crytic/slither/blob/master/README.md) confirms DOT graph printers are presentation outputs, not a persistence contract. Aderyn remains finding evidence unless a versioned structural output is demonstrated.

For the Next.js 16/React 19 UI, Phase 4 **selected React Flow** because custom React nodes, grouped subflows, keyboard interaction and accessibility hooks suit a source-linked security research interface ([features](https://reactflow.dev/examples/overview), [subflows](https://reactflow.dev/learn/layouting/sub-flows), [accessibility](https://reactflow.dev/learn/advanced-use/accessibility)). It needs filtering/collapsing and performance work for thousands of visible nodes ([performance guidance](https://reactflow.dev/learn/advanced-use/performance)). **Cytoscape.js** offers mature graph traversal/layout and canvas rendering, but its imperative model needs a React adapter and compound nodes add rendering cost ([documentation](https://js.cytoscape.org/)). **Sigma.js** uses WebGL for much larger graphs but also requires Graphology and more custom work for rich node drill-down and accessible interaction ([rendering](https://www.sigmajs.org/concepts/rendering/), [data model](https://www.sigmajs.org/docs/advanced/data/)). React Flow is installed only in the web package. Phase 4 bounds rendering and tests a representative large adapter/layout fixture; browser-level performance testing on real large protocols remains useful.

| Phase 4 criterion | React Flow | Cytoscape.js | Sigma.js |
| --- | --- | --- | --- |
| React/Next.js and maintenance | Direct React component model; keep it client-side in Next.js | Imperative canvas API needs a lifecycle adapter | Imperative WebGL renderer plus Graphology adapter |
| Hundreds to thousands of nodes | Strong for focused/filtered views; collapse groups and benchmark dense views | Designed for graph interaction at this scale; compound nodes cost more | Strongest raw rendering headroom for very large graphs |
| Custom security nodes and interaction | React components, selection, zoom/pan, grouping, filtering and path styling fit drill-down | Rich selectors/traversal and layouts; custom HTML-like panels need separate UI | Efficient highlighting/filtering; rich node cards need separate UI/WebGL work |
| Layout | External ELK/Dagre integration | Built-in and extension layouts | External layout through Graphology ecosystem |
| Accessibility | Documented keyboard and screen-reader controls | Requires a separate accessible list/detail surface for this product | Requires a separate accessible list/detail surface for this product |
| Dependency/bundle cost | One renderer plus likely layout dependency; measure actual bundle in Phase 4 | One renderer plus optional extensions/React adapter | Renderer, Graphology and layout/custom accessibility code |

Layout is separate from rendering. Phase 4 installs **Dagre** for stable left-to-right contract-level layouts. Compound groups are deferred; if Phase 5 or later needs them, ELK is the likely next evaluation because Dagre has a documented subflow limitation when edges cross groups ([React Flow layout comparison](https://reactflow.dev/learn/layouting/layouting)).

Graph/map facts do not verify hypotheses, alter severity/confidence, create evidence or move lifecycle state. The current Impact Lab Compose worker rebuild/live smoke remains a separate v0.3 release gate.
