# Security model

ContractHunter is a single-user local tool for authorised analysis. It has no application authentication; do not expose the web port to an untrusted network. Repository content is hostile input. Dependency preparation accepts only approved pinned Git submodules and lockfile-backed npm dependencies with lifecycle scripts disabled. AI receives bounded context and can propose structured data, but has no command, filesystem, RPC, wallet, or verification execution authority.

## v0.1.9 verification boundary

The web service validates persisted scan and hypothesis state, builds a deterministic workspace from an allowlisted Solidity source closure, writes its own `foundry.toml` with `ffi = false`, checks file hashes, and sends only job identifiers and bounded limits over a Unix-domain socket. It interprets execution facts and owns all dynamic evidence and lifecycle transitions. A successful process alone cannot verify a hypothesis; only completed, confirmed, valid supporting dynamic evidence can do so.

The separate `verification-worker` has `network_mode: none`, no ports, no Compose network, no Docker socket, and no application API credentials. It runs as UID 10002 with the shared ContractHunter GID 10001, a read-only root filesystem, bounded tmpfs, a one-CPU quota, `pids_limit: 64`, no capabilities, `no-new-privileges`, and Docker's default seccomp and enforcing AppArmor profile. It receives only the verification workspace volume, a small socket volume, and the read-only `tool-home` subpath of the existing data volume. The main database and repository store are not mounted.

A separate one-shot `contracthunter-data-init` service runs as UID/GID 10001:10001 without networking, ports, secrets, or capabilities. It mounts the main data volume read/write only to ensure `/data/tool-home` is usable before the worker starts. Compose may pre-create an empty root-owned subpath; the initializer can replace that empty directory, but fails closed rather than changing a populated cache it cannot write. It does not inspect repositories or modify the database. The worker still sees only the read-only tool-home subpath.

At startup and before every job the worker checks its UID/GID, zero effective and bounding capabilities, `NoNewPrivs=1`, seccomp mode 2, enforcing AppArmor, cgroup PID limit, loopback-only interfaces, lack of usable default routes, forbidden environment keys, and absence of database, repository, and Docker socket paths. A failed check prevents Forge execution. The Unix socket is group-owned and mode 0660. The RPC is length-prefixed JSON with a 4096-byte request cap, strict schema, one `verify` command, UUID workspace identifier, and no source or arbitrary command arguments.

The worker revalidates the workspace realpath, strict manifest identity, source and harness hashes, exact generated configuration, expected layout, and trusted compiler. The compiler must be the exact regular, non-symlink solc-select artifact below the read-only cache, must execute `--version` successfully, and must report the requested stable version. Forge runs with fixed `test --color never` arguments and an optional sanitized `--match-test` identifier. The child environment is constructed from scratch with offline compiler selection, FFI disabled, one ContractHunter-owned Foundry thread, and no proxy, secret, wallet, or RPC variables. `prlimit` bounds CPU time, virtual memory, file descriptors, and file size; the controller bounds wall time and captured output. Process count is enforced by the worker's independently checked 64-task cgroup rather than per-UID `RLIMIT_NPROC`, because that host-global limit can make isolated Compose projects interfere when their containers share numeric UID 10002. The one-CPU Compose quota keeps pinned Forge 1.7.1's compiler thread pool within the same 64-task cgroup.

Nested Bubblewrap verification was retired because Docker's masked/read-only `/proc` mounts blocked Bubblewrap's new proc mount even after its namespace creation succeeded. No custom mount/namespace seccomp rule, broad AppArmor mount permission, unconfined Docker setting, privileged mode, host network, Docker socket, or dynamic container spawning is used. The web retains ordinary networking for scanning and optional AI, and cannot run verification Forge as a fallback.

## v0.2.0 Milestone 1 boundary

The internal `contracthunter-invariant-plan-v1` schema accepts only bounded structured operations. Fuzz inputs are `uint256` or `bool`; addresses are symbolic actors or named deployed instances. Setup allows no-argument deployments of the primary contract, bounded native funding, and typed calls. Handler actions target specific validated functions. Properties use typed current-state reads and equality or inequality checks against constants, symbolic addresses, or another observation. Assumptions and arbitrary Solidity are deferred. Collections, identifiers, source paths, funding, and function signatures are checked before generation. The generator internally emits only `vm.prank` and `vm.deal` as needed, plus the fixed `targetContract` helper; it never accepts cheatcode names from a plan.

Invariant workspaces keep offline compiler selection, disabled autodetection and FFI, empty filesystem permissions, no remapping discovery, and fixed ContractHunter-controlled fuzz/invariant settings. The seed is the SHA-256 canonical plan hash, written to `[fuzz].seed`; Foundry 1.7.1 uses that fuzz seed for its invariant runner as well. The manifest records identity, mode, schema, source and harness hashes, config hash, seed, and a content fingerprint.

## v0.2.0 Milestone 2 execution boundary

Invariant jobs use the same networkless, non-root, capability-free, read-only-root worker and Unix socket as v0.1.9 verification. The request is a strict explicit command, not a command runner. A version 2 manifest embeds the bounded plan; the worker checks plan identity and hash, regenerates harness/config bytes from source, checks source hashes and file types, verifies trusted cached solc, and then runs a fixed offline Forge command. The original verification manifest remains valid. CPU time is 181 seconds, address space 2 GiB, process limit 64, open files 256, output file size 64 MiB, wall time 180 seconds, and captured output 2 MiB. Docker `pids_limit=64` remains.

Only complete, untruncated, expected Forge 1.7.1 JSON test facts become evidence. A failed generated property with a bounded counterexample contradicts that property; a pass supports that it held within configured runs/depth. Neither outcome automatically changes hypothesis status. Worker refusal, compiler mismatch, timeout and unparseable output fail closed. There is no web-container Forge fallback.

## v0.2.0 Milestone 3 proposal boundary

AI is manually invoked once per proposal request, without tools, retries, or reviewer fan-out. Its strict output contains only semantic invariant operations and a short rationale. It cannot specify scan/hypothesis IDs, commit, compiler, source paths, Solidity, imports, cheatcodes, Foundry options, executable commands, RPC, FFI, or raw addresses. The server uses persisted identity and validated source evidence, chooses one compatible trusted compiler without downloading it, and rejects unsupported semantics rather than rewriting them. Provider payload and source text are not stored in proposal history or logged on failure.

Proposal history is immutable. A generated proposal is not executable until a separate validation request rechecks identity, source hashes, compiler mapping, schema, and Solidity signatures. Local execution requires another explicit POST and uses the unchanged networkless worker protocol. Neither proposal generation nor invariant execution updates hypothesis status. The application remains a single-user local tool without application authentication; keep its web port on a trusted local interface.

## v0.2.0 Milestone 4 replay boundary

Property truth and hypothesis relevance are distinct. Fuzz execution determines only whether a property held within bounds or produced a counterexample. A counterexample is `unreviewed`; held-within-bounds is `neutral` and never rejects a hypothesis or lowers confidence. The proposal schema supports only `hypothesis-predicts-property-violation`, and the server accepts no AI-assigned evidence authority.

Replay values come only from a completed persisted worker result. Counterexamples contain typed bounded values or ordered allowlisted handler action IDs and are hashed canonically with a pinned parser version. Any changed value, bool, action, order, original plan, commit, compiler, harness, configuration, or manifest fails revalidation. The generated test positively asserts the expected violation and has no fuzz parameters, arbitrary source, browser values, imports, commands, Forge flags, FFI, RPC, fork, wallet, or filesystem authority.

Replay uses the existing networkless worker, trusted compiler resolver, offline environment, Unix socket, `prlimit`, read-only root, capability restrictions, and fixed `forge test --json` command. A reproduced replay remains non-authoritative until the local user confirms that the violation materially supports the stated hypothesis. The immutable review creates authoritative evidence; only centralized lifecycle logic can transition an eligible hypothesis. Failed, refused and not-reproduced histories remain preserved without status changes. Replay and review make no AI calls.
