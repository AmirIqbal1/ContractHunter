# Security model

## G1 package authority and redaction

The browser submits only exact canonical subject/execution/scenario/replay selectors. The server verifies same-scan ownership and authoritative PoC/session/E1/F1/F2 bindings, then copies only allowlisted evidence fields. It excludes upstream and local RPC endpoints, credentials, disposable keys, raw runtime tokens, worker/process internals, Docker control data, and host paths. PoC source or source excerpts with detected sensitive text are omitted with an explicit warning. Frozen packages have database update/delete guards, canonical manifest and content hashes, and a core integrity verifier; these hashes do not constitute signatures. Source, revert, token, finding, and annotation text remains untrusted plain data in React. Draft creation, finalization, reads and download never invoke the PoC/replay controller, fork lifecycle, worker or RPC. The production Compose Impact worker rebuild and live local-fork smoke gate remains open for v0.3.

## Impact Lab Phase F2B result-view boundary

The run result route checks the scan, source execution, scenario, plan and run chain before rendering. It reads persisted F2A/C1/D1/E1/F1 evidence; all controls are local presentation state. The page cannot start, edit, increase or optimize replay. It renders token metadata, labels and revert/error text as React text, and passes only safe IDs/statuses to the browser. RPC URL, credentials, runtime token, worker secrets, host paths and Docker control data remain server-only. Missing accounting, restart and timeout do not become successful final-reset or zero-movement claims. No lifecycle, severity, pricing, TVL, maximum-drain, upstream or AI authority changes.

## Impact Lab Phase F2A replay authority

Replay requires a current reviewed F1 scenario, matching E1 hash, the exact reviewed B1 artifact and observation plan, and a live guarded fork with the original runtime token hash and fork identity. Browser input is strictly the closed two-mode choice and integer 2–5; it cannot supply source, transactions, sender, funding, target, endpoint or commands. The existing B1 worker retains its networkless, unprivileged, read-only-root Docker boundary, fixed Forge mode and per-job limits. A single controller lease excludes concurrent normal PoC execution for the full replay. The run checks a 10-minute server deadline before each bounded iteration, supports cancellation after the current iteration, never resumes after restart, and attempts final baseline reset; failure stops the fork. Replay evidence does not verify a finding, change confidence or assign severity. API/UI expose hashes and local evidence IDs, never RPC URLs, credentials, private keys, raw runtime tokens, worker secrets, Docker control or host paths.

## Impact Lab Phase F1 role-review boundary

Scenario APIs validate UUID hunt, execution, scenario, and revision IDs, then load the exact scan-owned E1 result and authoritative execution subject. Browser role input contains only bounded opaque E1-derived participant selectors and a closed role value. Unknown selectors, duplicates, zero-address assignment, stale E1 hashes, and non-current revisions are rejected. Draft preview is explicitly non-reviewed; only a reviewed current revision can be served by the read-only impact endpoint. Database triggers prevent updates or deletion of finalized revisions. Manual role labels are annotations, not ProtocolGraph identity or lifecycle evidence. Notes and graph labels render as React text. The API returns no private key, RPC credential/URL, runtime token, worker secret, Docker control, or host path. F1 cannot run PoCs, call RPC, assign severity, or verify findings.

## Impact Lab Phase E2 visual boundary

The nested Asset Flow route validates UUIDs and hunt existence, then uses the E1 exact execution ownership and evidence-integrity gate. Execution switching reloads that gate. The browser receives the existing E1 read model and presentation-only server projections; it submits no ledger, classification, pricing or execution input. Filters and grouping cannot alter canonical entries. Mapped navigation uses canonical IDs only; unmapped addresses receive no invented graph identity. React renders labels, addresses and event-derived text as plain text. No private keys, RPC URLs/credentials, runtime tokens, worker secrets, Docker internals or host paths are exposed. No new AI, execution or finding/lifecycle authority is added.

## Impact Lab Phase E1 accounting boundary

The E1 GET path accepts only UUID scan and execution IDs and reuses Phase 10's reviewed-artifact, fork-session, same-scan subject and C1/D1 content/provenance validation. The client supplies no ledger rules, standard bindings, trace, receipt or transaction hash. The server performs no RPC call or execution. Production supplies no trusted token-standard binding, so ambiguous Transfer events remain unknown-standard; reverted effects are excluded from committed ledger. Gas cost is unavailable without persisted effective gas price and is never mixed into asset transfer entries. Output contains exact addresses, raw integer values and bounded evidence IDs, with no runtime token hash, private key, RPC URL/credential, worker secret, Docker control or host path. The route sanitizes internal errors. Accounting does not verify a finding or alter confidence, severity, hypothesis lifecycle, ProtocolGraph, Impact Overlay or Impact Lab authority.

## Phase 10B presentation boundary

Execution selectors come from reviewed artifacts scoped to the scan and optional subject. A browser-supplied execution ID is checked against that list and then independently validated by the Phase 10A resolver; it cannot select another hunt's evidence. URL transaction/call/path IDs are admitted only if present in the loaded overlay/path. React escapes runtime revert text, calldata previews, topics, labels and addresses. The UI renders only D1 bounded previews and hashes; it does not request raw RPC responses. No raw runtime token, private key, upstream RPC URL, worker secret, Docker control data or host path is part of the overlay read model. An exact source link requires canonical graph mapping. Dynamic observations do not change finding state, hypothesis confidence/severity, ProtocolGraph, Investigation Path or Impact Lab authority.

## Impact Overlay boundary (Phase 10A)

The overlay reads only persisted reviewed PoC evidence from ContractHunter's isolated local fork. The API requires exact scan/execution/subject ownership and exposes no trace upload, execution command, RPC URL, runtime token, private key or worker control. It binds C1/D1 artifacts to execution, session, reviewed source, fork base block/hash and target code hashes, and returns only bounded observed local facts. The local receipt block is distinct from the fork base block. A static edge not seen in one capture is “not observed in this execution,” never unreachable. Unknown addresses, selectors, storage variables and event declarations remain unresolved. Delegatecall records code and storage context separately; trace/state co-occurrence is not causal attribution. Runtime evidence cannot mutate ProtocolGraph, Investigation Paths, findings, hypothesis confidence/severity/lifecycle or Impact Lab authority. Repository-derived and runtime strings render as escaped React text in Phase 10B. No AI mapping or live-chain submission is involved.

## Investigation Path UI boundary (Phase 9B)

The visual path is a read-only rendering of Phase 9A's bounded static result. Its arrows use only returned edge IDs and relationship kinds; unknown targets end without continuation. The exact target marker uses persisted finding-to-node membership. Entry-point wording means static connectivity, not runtime reachability or permissionless access. A path's presence cannot verify a finding, change status/confidence/severity, create dynamic evidence, assert financial impact, or authorize Impact Lab. Repository titles, signatures, reasons and labels render as React text; source links use canonical source units, never raw host paths. Beginner explanations come from the existing fixed concept catalog. C1 state and D1 traces remain separate observed overlays, never static path facts.

## Investigation Path boundary (Phase 9A)

An Investigation Path is a static, bounded navigation artifact. It joins exact finding-to-graph links with proven graph relationships and source/provenance. A caller chain means static connectivity only; it does not prove runtime reachability or exploitability. Contract-level fallback is never elevated to a function match. Oracle, asset and proxy context require existing deterministic evidence; unresolved calls do not receive invented targets. Derivation cannot change finding, Investigation or Hypothesis lifecycle, severity or confidence, create evidence, or authorize verification or Impact Lab. D1/C1 observations remain separate overlays. See [finding-integration-audit.md](finding-integration-audit.md).

## Beginner Mode boundary (Phase 8B)

Start Here presents the Phase 8A Audit Priority result without changing weights, scores, findings or graph truth. Both display modes show the same evidence. A higher score means more known characteristics worth manual review, not greater vulnerability likelihood. A low score is not a safety conclusion. Partial coverage and unresolved targets remain explicit. Fixed product text supplies concept help; repository strings render as React text. Canonical scan, contract, function and source identities drive navigation. Ranking grants no Impact Lab authority and creates no dynamic evidence.

## Audit-priority boundary (Phase 8A)

Audit Priority Score is a transparent 0–100 ordering of proven static characteristics for manual review. Every awarded point is assigned to a closed, versioned factor with existing graph, Security View, function-fact, classification or exact finding evidence. Bucket caps prevent raw function/finding counts from dominating. The score is **not** vulnerability likelihood, severity, exploitability, safety, profit or observed impact. Name-only asset/oracle/privilege guesses are excluded. Source-order write-after-call is not runtime execution proof. Missing Repository Map, incomplete analysis and unresolved targets remain warnings. Derivation is read-only: it cannot verify findings, change hypothesis state, create evidence, or launch Impact Lab. Phase 8B must keep these limits visible.

## Interactive Security View boundary (Phase 7B)

The Protocol Map renders Phase 7A projections as read-only filters of a validated static graph. It checks projection scan and graph identity before rendering and uses canonical IDs for drill-down. Repository strings and finding titles render as React text; no HTML insertion or arbitrary filesystem source route is used. Money Flow distinguishes static transfer-like evidence from observed movement and leaves asset direction unresolved. Oracle, role and proxy labels require existing evidence. Unresolved calls remain unresolved annotations; warnings and empty states do not assert absence or safety. View switching, search and focus do not update graph facts, finding authority, Impact Lab evidence or lifecycle state.

## Security View Phase 7A boundary

Security Views are read-only static projections, not evidence or vulnerability decisions. They reference only existing graph node/edge IDs, preserve source/evidence reasons and reject unknown view types. They do not alter graph facts, finding status, hypothesis confidence/severity/lifecycle, or Impact Lab authority. Unresolved targets remain unresolved; a call edge is not relabeled as an asset transfer. Names alone never establish money movement, oracle identity, role semantics, proxy status or exploitability. The API returns bounded metadata from exact same-scan finding IDs and sanitizes graph/derivation failures. Future observed C1/D1 facts remain separate from these static projections.

## Function Explorer Phase 6B UI boundary

The server rejects malformed or cross-contract function selectors and loads only the validated scan-bound Phase 6A artifact. Source previews use exact graph source-unit identity and checksum-matched immutable snapshot bytes. Repository-derived signatures, expressions, source and finding text render through React text escaping; no raw HTML or checkout path is exposed. Browser filters, mode and selection alter only presentation. The UI presents source order explicitly, marks partial analysis, and never treats a call, write, modifier, finding or review cue as proof of a vulnerability. Impact Lab execution, finding status, confidence, severity and lifecycle remain unchanged.

## Function Explorer Phase 6A boundary

The API accepts only canonical scan/contract/function IDs and rejects wrong ownership. The model reads validated immutable static graph artifacts and exact source-unit snapshots; a source preview is capped at 4 KiB and decoded as strict UTF-8. Repository-controlled expressions remain plain data, with bounded excerpts and SHA-256 identities. It executes no repository code, accepts no arbitrary source path, and has no Impact Lab, finding-status or lifecycle mutation authority. Source-order write/call cues are research prompts, not runtime path proofs or vulnerability verdicts. Missing syntax facts and collapsed state-access sites are reported as partial analysis.

## Protocol Intelligence Phases 1–5 foundation

The Repository Mapper treats cloned repository paths and Solidity bytes as hostile input. It never runs repository code, Hardhat configuration or package scripts. Traversal is bounded, symlinks are skipped, paths are canonical repository-relative names, and Solidity reads have a byte cap. Finalized scan snapshot bytes take precedence over mutable checkout content; unsnapshotted Solidity is marked `reported`, not authoritative. A conservative lexical pass can identify declaration candidates and imports for orientation, but it is not a Solidity compiler/AST and does not grant compiler authority. Detected unbalanced/malformed input is `incomplete` with no declarations; balanced but compiler-invalid syntax may still yield lexical candidates and must not be treated as validated contracts. Unsupported imports remain unresolved, and uncertain production contracts remain `unknown`. Exact aligned finding IDs are references only. The immutable map is bound to scan, commit, ruleset and source universe; reading verifies its content hash. Classification and future overrides affect navigation only: they cannot alter scanner evidence, hypothesis lifecycle, severity, source authority or Impact Lab execution.

ProtocolGraph parses bounded, closed data and requires source-unit, producer and relationship provenance. Reported source identity is distinct from authoritative scan snapshot/compiler identity. Base edges are static; finding and Impact Lab state/trace overlays can only refer to existing graph identities and cannot overwrite source facts. Security characteristics indicate audit interest, not vulnerability probability, severity or proof. Phase 1 performs no repository execution, AI call, graph extraction, worker privilege change, evidence admission or lifecycle transition. Phase 3 uses the already-approved cached compiler artifact, checked by SHA-256, with fixed standard-JSON AST settings over immutable snapshot bytes. It does not scrape DOT/terminal diagrams or execute dynamic repository build configuration. Unknown call/proxy targets remain unresolved. Graph facts do not gain vulnerability authority. Phase 4 reads only validated graph artifacts, uses React text escaping, enforces renderer bounds and keeps filters client-only. Source links require exact graph source-unit membership and immutable snapshot bytes; they never guess by basename or reopen a checkout. The UI cannot edit findings, evidence or lifecycle state. Phase 5 Contract Explorer reads only the validated graph for the requested scan; exact contract IDs and finding-link IDs determine associations. Cross-scan and malformed selectors fail closed. It uses React-escaped text, immutable snapshot source links, bounded relationship/function lists, and no arbitrary Impact Lab launch action. Review cues are structural navigation facts, never vulnerability scores or evidence. See [Protocol Map architecture](protocol-map.md).

## Impact Lab Phase D1 boundary

Only the controller can invoke the fixed managed-local-Anvil trace capability, after a reviewed job has supplied at most four transaction hashes through its guarded local bridge. The PoC worker, browser and upstream proxy cannot request `debug_traceTransaction`. Each local trace read reruns the central process/listener/session guard. Receipt transaction and block identities, sender, call root and execution/fork/token/source provenance are checked before persistence. Response, tree, depth, data, log, storage and time bounds fail closed. All traces for one execution are inserted atomically as finalized rows, or a separate failed capture status is recorded; partial trees are never public artifacts. Trace capture cannot promote evidence or lifecycle status. Existing worker isolation and the read-only upstream allowlist are unchanged.

## Impact Lab Phase C1 boundary

Observation plans are strict, bounded and controller-owned; the public selector accepts typed addresses, token IDs, exact slots and one fixed view descriptor only. The hostile PoC worker cannot alter observations or submit state values. Capture rechecks the central managed-Anvil guard on every local read and never uses provider URLs directly. The upstream proxy remains read-only. PRE failure prevents Forge, POST failure still triggers baseline reset, and partially captured data is not finalized as a complete diff. Snapshot/diff inserts and execution links are atomic; immutable triggers and read-time hash, row-count, provenance and derived-change checks reject tampering. Exact balances use decimal integer strings and BigInt deltas, so precision is retained. Zero observed changes confer no safety or vulnerability conclusion; no evidence, severity or lifecycle authority was added.

## Impact Lab Phase B1 boundary

B1's fixed Compose worker uses `network_mode: none` and no Docker socket, host networking, privileges, database, repository, secrets or wallet mount. The worker's nonroot/read-only/capability-free/seccomp/AppArmor/resource-bound profile is checked at startup. The only RPC it can reach is its in-container loopback bridge. A per-job Unix socket to the web controller is created after a ready-session guard and runtime-token check; each request repeats both checks. Only a closed local read allowlist plus at most four `eth_sendTransaction` calls from the disposable Anvil account can cross it. The upstream proxy still rejects all transaction submission and signing. Forge's optional `anvil_nodeInfo` and `eth_getAccountInfo` probes receive method-not-found without passthrough. No browser input controls RPC, command, image, env, wallet or Foundry flags. Source is bounded to one UTF-8 Solidity file, hashed, immutable once reviewed, and FFI is disabled. Execution records are reproduction data, never authoritative vulnerability evidence.

## Impact Lab Phase A3 boundary

The A2 provider boundary remains HTTPS configuration by `rpcConfigId` only, with a private localhost read-only proxy and an unchanged 18-method allowlist. A real Anvil 1.7.1 fork from a deterministic local fixture succeeded through that proxy. The fixture recorded seven forwarded read methods; Anvil's optional `eth_getAccountInfo` was denied and it recovered. The fork-only transaction and snapshot/revert did not reach the fixture.

A3 adds a separate Docker probe runtime, without changing the existing networkless verification worker. The probe accepts only a trusted active fork session ID, then pins its current runtime token. Its fixed image ID and schema are inspected. Docker `--network none` supplies only loopback, with no route to the proxy, host/LAN, public internet, or another fork. One private per-session Unix socket is the only mount and RPC path. The host bridge permits six bounded local read methods and rechecks token and managed-Anvil endpoint identity on every request. The probe runs as nonroot UID 10003, read-only root, capability-free, no-new-privileges, default seccomp/AppArmor, PID 32, half CPU, 128 MiB memory, and 16 MiB tmpfs; it has no Docker socket, database, repository store, provider URL, private key, or app secrets. Live container inspection and negative network probes verify these properties. Socket/token revocation and container removal accompany session stop/recreate. There is no PoC execution or browser-selectable command/image/RPC URL in A3.

This foundation is exercised by a host-side internal test harness. The standard Compose web service does not yet have an approved production controller for creating these containers; later PoC execution requires one without exposing the Docker daemon to a PoC container or weakening the verification worker.

ContractHunter is a single-user local tool for authorised analysis. It has no application authentication; do not expose the web port to an untrusted network. Repository content is hostile input. Dependency preparation accepts only approved pinned Git submodules and lockfile-backed npm dependencies with lifecycle scripts disabled. AI receives bounded context and can propose structured data, but has no command, filesystem, RPC, wallet, or verification execution authority.

## v0.1.9 verification boundary

The web service validates persisted scan and hypothesis state, builds a deterministic workspace from an allowlisted Solidity source closure, writes its own `foundry.toml` with `ffi = false`, checks file hashes, and sends only job identifiers and bounded limits over a Unix-domain socket. It interprets execution facts and owns all dynamic evidence and lifecycle transitions. A successful process alone cannot verify a hypothesis; only completed, confirmed, valid supporting dynamic evidence can do so.

The separate `verification-worker` has `network_mode: none`, no ports, no Compose network, no Docker socket, and no application API credentials. It runs as UID 10002 with the shared ContractHunter GID 10001, a read-only root filesystem, bounded tmpfs, a one-CPU quota, `pids_limit: 64`, no capabilities, `no-new-privileges`, and Docker's default seccomp and enforcing AppArmor profile. It receives only the verification workspace volume, a small socket volume, and the read-only `tool-home` subpath of the existing data volume. The main database and repository store are not mounted.

A separate one-shot `contracthunter-data-init` service runs as UID/GID 10001:10001 without networking, ports, secrets, or capabilities. It mounts the main data volume read/write only to ensure `/data/tool-home` is usable before the worker starts. Compose may pre-create an empty root-owned subpath; the initializer can replace that empty directory, but fails closed rather than changing a populated cache it cannot write. It does not inspect repositories or modify the database. The worker still sees only the read-only tool-home subpath.

At startup and before every job the worker checks its UID/GID, zero effective and bounding capabilities, `NoNewPrivs=1`, seccomp mode 2, enforcing AppArmor, cgroup PID limit, loopback-only interfaces, lack of usable default routes, forbidden environment keys, and absence of database, repository, and Docker socket paths. A failed check prevents Forge execution. The Unix socket is group-owned and mode 0660. The RPC is length-prefixed JSON with a 4096-byte request cap, strict schema, one `verify` command, UUID workspace identifier, and no source or arbitrary command arguments.

The worker revalidates the workspace realpath, strict manifest identity, source and harness hashes, exact generated configuration, expected layout, and trusted compiler. The compiler must be the exact regular, non-symlink solc-select artifact below the read-only cache, must execute `--version` successfully, and must report the requested stable version. Forge runs with fixed `test --color never` arguments and an optional sanitized `--match-test` identifier. The child environment is constructed from scratch with offline compiler selection, FFI disabled, one ContractHunter-owned Foundry thread, and no proxy, secret, wallet, or RPC variables. `prlimit` bounds CPU time, virtual memory, file descriptors, and file size; the controller bounds wall time and captured output. Process count is enforced by the worker's independently checked 64-task cgroup rather than per-UID `RLIMIT_NPROC`, because that host-global limit can make isolated Compose projects interfere when their containers share numeric UID 10002. The one-CPU Compose quota keeps pinned Forge 1.7.1's compiler thread pool within the same 64-task cgroup.

Nested Bubblewrap verification was retired because Docker's masked/read-only `/proc` mounts blocked Bubblewrap's new proc mount even after its namespace creation succeeded. No custom mount/namespace seccomp rule, broad AppArmor mount permission, unconfined Docker setting, privileged mode, host network, Docker socket, or dynamic container spawning is used. The web retains ordinary networking for scanning and optional AI, and cannot run verification Forge as a fallback.

## v0.2.0 Milestone 1 boundary

The internal `contracthunter-invariant-plan-v1` schema accepts only bounded structured operations. Fuzz inputs are `uint256` or `bool`; addresses are symbolic actors or named deployed instances. Setup allows no-argument deployments of the primary contract, bounded native funding, and typed calls. Handler actions target specific validated functions. Properties use typed current-state reads and equality or inequality checks against constants, symbolic addresses, or another observation. Assumptions and arbitrary Solidity are deferred. Collections, identifiers, source paths, funding, and function signatures are checked before generation. The generator internally emits only `vm.prank` and `vm.deal` as needed, plus the fixed `targetContract` helper; it never accepts cheatcode names from a plan.

Invariant workspaces keep offline compiler selection, disabled autodetection and FFI, empty filesystem permissions, no remapping discovery, and fixed ContractHunter-controlled fuzz/invariant settings. The seed is the SHA-256 canonical plan hash, written to `[fuzz].seed`; Foundry 1.7.1 uses that fuzz seed for its invariant runner as well. The manifest records identity, mode, schema, source and harness hashes, config hash, seed, and a content fingerprint.

## v0.2.0 Milestone 2 execution boundary

Invariant jobs use the same networkless, non-root, capability-free, read-only-root worker and Unix socket as v0.1.9 verification. The request is a strict explicit command, not a command runner. A version 2 manifest embeds the bounded plan; the worker checks plan identity and hash, regenerates harness/config bytes from source, checks source hashes and file types, verifies trusted cached solc, and then runs a fixed offline Forge command. The original verification manifest remains valid. CPU time is 181 seconds, address space 2 GiB, process limit 64, open files 256, output file size 64 MiB, wall time 180 seconds, and captured output 2 MiB. Docker `pids_limit=64` remains.

Only complete, untruncated, expected Forge 1.7.1 JSON test facts become evidence. A failed generated property with a bounded counterexample contradicts that property; a pass supports that it held within configured runs/depth. Neither outcome automatically changes hypothesis status. Worker refusal, compiler mismatch, timeout and unparseable output fail closed. There is no web-container Forge fallback.

## v0.2.0 Milestone 3 proposal boundary

AI is manually invoked once per proposal request, without tools, retries, or reviewer fan-out. Its strict output contains only semantic invariant operations and a short rationale. It cannot specify scan/hypothesis IDs, commit, compiler, source paths, Solidity, imports, cheatcodes, Foundry options, executable commands, RPC, FFI, or raw addresses. The server uses persisted identity and validated source evidence, chooses one compatible trusted compiler without downloading it, and rejects unsupported semantics rather than rewriting them. Provider payload and source text are not stored in proposal history or logged on failure.

Proposal history is immutable. A generated proposal is not executable until a separate validation request rechecks identity, source hashes, compiler mapping, schema, and Solidity signatures. Local execution requires another explicit POST and uses the unchanged networkless worker protocol. Neither proposal generation nor invariant execution updates hypothesis status. The application remains a single-user local tool without application authentication; keep its web port on a trusted local interface.

## v0.2.0 Milestone 4 replay boundary

Property truth and hypothesis relevance are distinct. Fuzz execution determines only whether a property held within bounds or produced a counterexample. A counterexample is `unreviewed`; held-within-bounds is `neutral` and never rejects a hypothesis or lowers confidence. The proposal schema supports only `hypothesis-predicts-property-violation`, and the server accepts no AI-assigned evidence authority.

Replay values come only from a completed persisted worker result. Counterexamples contain typed bounded values or ordered allowlisted handler action IDs and are hashed canonically with a pinned parser version. Any changed value, bool, action, order, original plan, commit, compiler, harness, configuration, or manifest fails revalidation. The generated test positively asserts the expected violation and has no fuzz parameters, arbitrary source, browser values, imports, commands, Forge flags, FFI, RPC, fork, wallet, or filesystem authority.

Replay uses the existing networkless worker, trusted compiler resolver, offline environment, Unix socket, `prlimit`, read-only root, capability restrictions, and fixed `forge test --json` command. A reproduced replay remains non-authoritative until the local user confirms that the violation materially supports the stated hypothesis. The immutable review creates authoritative evidence; only centralized lifecycle logic can transition an eligible hypothesis. Failed, refused and not-reproduced histories remain preserved without status changes. Replay and review make no AI calls.

## v0.2.1 Milestone 1 Echidna boundary

The Echidna operation runs in that same worker, with the same network, UID, root filesystem, capability, seccomp, AppArmor, PID, CPU, mount, and secret restrictions. The worker starts only after checking the root-owned static Echidna executable's exact path, type, mode, SHA-256, upstream version, and compatibility build ID. The patched binary is built from a pinned source archive and upstream locked Nix flake. Its `crytic-compile` Python frontend is installed from hash-locked wheels during image build. Neither tool downloads anything at runtime.

The request carries only authoritative UUIDs, commit/compiler identity, and plan hash. Version 3 Echidna workspaces contain only generated Solidity/config and the allowlisted source closure. The worker regenerates exact bytes and rejects symlinks, extra files, wrong hashes, or incompatible semantics before execution. Its fixed command passes the resolver's exact cached solc path to `crytic-compile`; it never uses a repository compiler, arbitrary PATH solc, RPC, FFI, forks, wallets, proxies, or shell execution. Missing solc fails as `trusted_compiler_unavailable`; an empty compiler cache does not prevent worker startup.

Only the patched compatibility JSON schema is accepted. Property identity comes from Echidna's typed test object. Terminal outcomes come from internal state and stop reason; exit status, console prose, and single-property assumptions cannot create evidence. Malformed, truncated, duplicated, unknown, or contradictory results fail closed. Unknown actions and malformed uint/bool arguments reject the result. A terminal failure with an otherwise valid but noncanonical sender, destination, value, or delay remains a bounded observation with `replayAvailable=false`. Exact ordered transactions are replayable only when they map to generated actions and typed values under the allowed sender/destination and zero value/delay rules. Held-within-bounds remains neutral. The existing deterministic Foundry replay and explicit human relevance confirmation remain the sole path to authoritative evidence; no lifecycle rule changed.

## v0.2.1 Milestone 2 public boundary

Validation exposes deterministic compatibility without running an engine. Foundry remains available for its full fuzz/stateful plan set. Echidna is manually selectable only for the Milestone 1 compatible stateful subset; incompatibility is displayed and refused before workspace creation. Both execution routes require empty bodies and reject actual unexpected or oversized bytes, so browser input cannot set binaries, arguments, compiler, source paths, plan, seed, budget, timeout, config, or counterexample. There is no silent fallback or combined run. The explicit persisted engine must match normalized evidence. Replay provenance binds the source engine and run to the canonical counterexample, while the same Foundry replay and centralized review/lifecycle checks remain authoritative. Historical Foundry records use an additive default and are not rewritten.

## v0.2.1 Milestone 3 Part 1 hardening

Startup applies all pending schema migrations and integrity checks in one transaction and refuses application access if any step fails. Public history fails closed when persisted run engine, canonical plan, evidence identity, Echidna seed, or replay provenance disagrees; it does not infer an engine from output. Replay execution rechecks the persisted source run, proposal, plan hash, compiler, commit, source engine, and counterexample before the worker call. The operator-only retention command requires a recognized manifest for the database-backed workspace kind and keeps active, recent failed/refused, unknown, and symlinked workspaces. Live isolated Compose inspection reconfirmed a networkless, read-only-root worker with UID/GID `10002:10001`, no capabilities, no new privileges, seccomp and enforcing AppArmor, one CPU, a 64-task cgroup limit, a read-only compiler-cache mount, and no database, repository store, Docker socket, ports, secrets, or proxy keys.

## v0.2.2 Milestone 2 Part 2B-00A scan-source boundary

New scans capture a bounded raw-byte Solidity source universe after commit resolution and trusted dependency preparation. Only safe keys beneath `src`, `contracts`, `lib`, or supported imported `node_modules` paths enter the versioned `contracthunter-scan-source-snapshot-v1` manifest. Host absolute paths, traversal, escapes, file symlinks, directory symlink loops, duplicate physical aliases, oversized files, and excessive source counts/bytes fail closed. Repository scripts, source code, RPC, workers, and AI are not invoked by capture. SHA-256 is computed directly over raw bytes, so line endings and invalid UTF-8 remain distinct.

SQLite BLOB rows and the manifest finalize atomically; finalized membership and bytes are immutable. The reader never opens a checkout or falls back to the working tree. Legacy scans return an explicit unavailable result and are never backfilled from mutable files. Scan deletion cascades snapshot rows. At this milestone the snapshot alone did not authorize planning-time byte identity or artifact reuse; Part 2B-00B later replaced the supported planners' and workspace builders' checkout resolution path with snapshot-backed closure resolution.

## v0.2.2 Milestone 2 Part 2B-00A4 compilation boundary

The scanner checkout and scanner-private project detection do not establish authoritative compilation. ContractHunter's initial authority is a narrow plain Solidity profile with exact matching pragmas and snapshot-backed `src`/`contracts` source units. Root Hardhat configuration is never executed for authority. Foundry and remapping behavior are unsupported until explicitly modeled; ambient `FOUNDRY_PROFILE`, automatic remapping discovery, package scripts, and shell configuration have no authority. Unsupported provenance leaves ordinary static scanning and existing manual planning available, but cannot qualify a finding for future snapshot-backed verification or reuse.

The probe invokes only the previously trusted, cached solc-select artifact by exact path with fixed `--standard-json` arguments, a clean environment, bounded input, time, and output, and no file callback. It reads Solidity bytes from the finalized scan snapshot, records the compiler artifact SHA-256 and exact source-unit membership, and rejects compiler errors or mismatched output membership. It does not execute compiled bytecode, scripts, AI, wallets, or RPC. Successful scanner execution is independent of supported authoritative compilation. Per-finding alignment is exact and bounded; ambiguous basename paths and unknown contracts fail the future eligibility condition. ## v0.3 Phase A1 fork boundary

Impact Lab distinguishes the HTTPS upstream fork-source RPC from the loopback Anvil execution RPC as separate model fields and service paths. An application-owned proxy accepts only a closed read-method set; it rejects `eth_sendTransaction`, `eth_sendRawTransaction`, wallet/admin mutation methods, and mixed batches before any upstream fetch, with no redirect following. Neither browser input nor persisted rows can set an Anvil executable, argument vector, raw upstream URL, local execution URL, or RPC method policy. The internal service accepts only a bounded `IMPACT_RPC_*` reference and exact block, resolves an approved trusted Anvil binary without download, and starts it with `shell: false`, a clean environment, localhost bind, fixed arguments, output/lifetime bounds, and Linux parent-death/process-group cleanup.

The central execution-endpoint guard requires an active in-memory session token, the owned process start identity and loopback listening socket, Anvil client identity, matching chain ID, and matching pinned block hash. A localhost URL alone is insufficient. Snapshot/revert/reset and address-validated impersonation call only this guard. Failures remove readiness and attempt cleanup. Audit rows omit provider URLs, secrets, mnemonics, and private keys; stale active rows become failed after restart. Phase A1 exposes no public Impact API or PoC execution. The existing networkless verification worker is unchanged. A future PoC runtime additionally needs independent egress isolation so it cannot bypass the upstream filter.
